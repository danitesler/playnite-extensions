# Playnite extensions monorepo — agent handoff

## Overview
Playnite add-on monorepo registered in `src/extensions.json`:
- **Plugins** (`plugin`): .NET WPF extensions under `src/<PluginName>/`.
- **Themes** (`theme`): XAML themes under `src/themes/<ThemeName>/` sharing `scripts/data/theme-keys.json` keys.
Active add-ons catalog is in `src/extensions.json`. Per-extension notes live in `src/<dir>/AGENTS.md`.

## Layout & Data Sources
- **Index**: `src/extensions.json` (key, name, kind, dir, AddonId, API version)
- **Plugins**: `src/<PluginName>/` (`src/`, `info/`) | **Themes**: `src/themes/<ThemeName>/` (`src/`, `info/`)
- **Key Data**: `scripts/data/theme-keys.json`, `scripts/data/playnite-theme-api.json`
- **Artifacts**: `artifacts/releases/` and `artifacts/builds/`

## Key Commands
- Validate: `.\scripts\validate-extension.ps1 -Extension <key>`
- Build plugin: `.\scripts\build-plugin.ps1 -Extension <key>`
- Package: `.\scripts\build-artifacts.ps1 -Extension <key> -VerifyInstaller`
- Scaffold plugin: `.\scripts\new-extension.ps1 -Name MyPlugin -Key myplugin -Type GenericPlugin -Author <name>`
- Build theme: `.\scripts\build-theme.ps1 -Extension <key> [-Deploy] [-Restart]`
- Scaffold theme: `.\scripts\new-theme.ps1 -Name "My Theme" -Key mytheme [-DesignSystem "My DS"] [-TokensCss <css>]`
- Render icons: `.\scripts\render-icons.ps1 -Extension <key>`
- Tile icon: `.\scripts\render-addon-icon.ps1 -Svg logo.svg -Extension <key>`
- Screenshots: `.\scripts\take-screenshots.ps1 -Extension <key>` (renders `screenshot-details.png` & `screenshot-settings.png` from HTML)
- Add-on READMEs: `node scripts/generate-readmes.mjs` (`--check` or `npm run check:readmes` to verify; fetch tags first)
- Update API snapshot: `.\scripts\update-playnite-theme-api.ps1 -PlayniteSource <path> -PlayniteVersion <tag>`
- Run unit tests: `dotnet test tests/Tests.csproj`
- All checks: `pwsh scripts/check-all.ps1` (Windows) or `scripts/check-all.sh` (Linux): validate + build every plugin and theme, unit tests, READMEs, preview checks. Run before merging or releasing. **There is no hosted CI. Never add GitHub Actions workflows** (or Dependabot or any other `.github/` automation).

## Strict Mandates
- **Build after edit (Windows: always Deploy + Restart)**: After every update to a theme or plugin (code, tokens, XAML, previews, manifests), when working on a Windows machine, always finish with a deploy build. Themes: run `.\scripts\build-theme.ps1 -Extension <key> -Deploy -Restart` (auto-sets active theme and restarts/launches Playnite on local Windows). Plugins: run `.\scripts\build-plugin.ps1 -Extension <key>` (remind user to replace DLL). Never end an update on a bare build on Windows.
- **Always Deploy on Build**: Whenever the user asks to build a theme (even just "build"), always run `build-theme.ps1` with `-Deploy -Restart`. Never do a bare build unless explicitly told "no deploy". For "build all themes", build each, then deploy+restart only the theme currently being worked on (deploy sets the active theme, so only one can be active). Playnite loads the **deployed copy** (`%AppData%\Playnite\Themes\Desktop\<Id>`), never the repo source or `artifacts/builds`: a batch build alone leaves every other theme stale, so after a change that spans themes redeploy each one (`build-theme.ps1 -Extension <key> -Deploy`, no restart) before checking it in the app.
- **No Server Execution**: Never run/install/emulate Playnite on non-Windows/server environments.
- **Releases**: Package-only (`.pext`/`.pthm` + `.zip`). Tag `{key}-v{version}`. Never push, tag, release, or open PR unless asked.
- **Add-on READMEs & Release Links**: Every add-on has a `README.md` in its folder (overview, screenshots, install, details), and every add-on row in the root `README.md` ends with `Details` (always) and `Download <version>` (only when the `{key}-v{version}` tag exists; otherwise plain "not released yet"). Both are produced by `node scripts/generate-readmes.mjs` from `info/danitesler_<key>.yaml`, the manifests and the git tags; never edit a generated README by hand (it starts with a `Generated by` marker). After cutting a release (tag exists), run the script and commit the result. A hand-written README (RandomTheme) is kept as is. The root row text (name and description) stays hand-written; the script rewrites the row's image link (the theme preview or plugin icon opens that add-on's Details page, never the image file) and its links line. `scripts/check-all.ps1` fails when generated files are out of date (`npm run check:readmes`).
- **Localization**: New strings go to `en_US.xaml` AND all `Localization/*.xaml`.
- **Settings UI**: Prefer Playnite native components; stock controls only. Autogrid `SettingsView` is baseline. Use native `TabControl`/`TabItem`, `Separator`, `CheckBox`, `Label`, `Slider`, `RadioButton`, `ComboBox`, `TextBox`, `Button`, `TextBlock` with `StackPanel`/`Grid` layout — no custom templates, cards, pills, tab strips, toggles, icon buttons, pickers, or shadows. Theme brushes/sizes via `{DynamicResource ...}` (`TextBrush`, `PopupBackgroundBrush`, `PopupBorderBrush`, `FontSize`); never hardcoded hex, `FontSize`, or `FontWeight`.
- **Statistics Page (compact cards)**: Playnite's Statistics view lays its sections (Overview, Completion Status, Top play time, Library, ...) out as `GroupBox`es in a wrapping panel, so every section is a compact card sized by its content, several per row. Never restyle that view, and never give a `GroupBox` template a child that reports a large desired width: a `Path` or `Line` with `Stretch="None"`/`Fill` wider than ~200px (hazard stripes, rules, ornaments), a fixed `Width`/`MinWidth` >= 200, `HorizontalAlignment="Stretch"` plus a fixed-size art, or a `Control` whose template does any of these (`Template="{DynamicResource ...}"`). One such child makes every section ask for the whole page, so the cards stack full width with large empty areas (hit Blacklist's 2600px hazard Path, Cordon's `Line`). Follow Ayywi's `DefaultControls/GroupBox.xaml`: a content-sized `Border` with a header and a body, no fixed widths. Decoration that must span the card goes inside a `Canvas` (no desired size) in a `Grid` with `ClipToBounds="True"`; use `Rectangle`/`Border` for rules. Any shared template used in a GroupBox (dividers, stripes, chamfers) follows the same rule. After touching `GroupBox.xaml`, a template it uses, or `HazardStripesTemplate`-style art, open Statistics in Playnite and check the sections wrap as cards. `validate-extension.ps1` flags wide Paths, `Line Stretch=Fill` and fixed widths >= 200 in the GroupBox template and the templates it references.
- **ComboBox chevron room**: In a `ComboBox` template the selected value (`ContentSite`) and the dropdown chevron share one cell, and the box is only as wide as its value, so a value with no space reserved on its right runs under the arrow and the chevron looks hidden (Blacklist's "English", "Minimize"). Always reserve the chevron: wrap `ContentSite` in a `Border` with `Margin="0,0,R,0"` where R = chevron width + its right margin + 8px (or put the value and the chevron in separate grid columns, as Ayywi does), and keep `PART_EditableTextBox`'s right margin equal to R. `validate-extension.ps1` fails a `ComboBox.xaml` whose `ContentSite` reserves less than 12px on its right. Check a short value ("Minimize") and a long one in Settings after touching the template.
- **Game page action buttons**: Next to Play on the game page (details view and grid side panel), the secondary buttons (`PART_ButtonMoreActions`, `PART_ButtonEditGame`, and any other secondary action) are **icon-only**: a glyph from `Media.xaml` (`IconOptions`, `IconEdit`) in a fixed-width square button (`Padding="0"`), no text label; the label goes in `ToolTip` (`LOCMoreAction`, `LOCEditGame`). Play (and the context action) keep their text. More and Edit are the **same fixed square** (`Width == Height`, identical on both, e.g. 40x40) and both carry a `ToolTip` (More / Edit) so hovering names them. The Edit button is **always visible**: never hide it (`Visibility="Hidden"`/`Collapsed`) or reveal it on hover (a `DataTrigger` on `IsMouseOver` of an ancestor), so ThemeModifier-style discoverability and touch work. `validate-extension.ps1` fails a labeled More button, a hover-only Edit button, unequal More/Edit sizes and a missing ToolTip.
- **Theme Shell Layout**: Sidebar on Left (compact rail: 44px wide, 44x40 items, 16px glyphs).
- **Control Corner Radii**: In WPF, `CornerRadiusFull` (9999/10000) clamps X and Y radii independently to `width/2` and `height/2`, distorting any element where `width != height` into a stretched oval/ellipse instead of a true capsule. Therefore, never use `CornerRadiusFull` on base control styles (`Button`, `RepeatButton`, `ToggleButton`, `SearchBox`, `TabControl`, menu items), action buttons (`PlayButton`), or metadata tag chips (`PropertyItemButton`). All of these must use `ControlCornerRadius` (or `CornerRadiusSmall`). Thin tracks and progress fills (`Slider` tracks, `ProgressBar`, tab indicator lines, `ScrollBarThumb`) must also NEVER use `CornerRadiusFull` (which turns the track into an elongated needle/spindle); always specify an explicit numeric radius equal to half the track thickness (e.g. `CornerRadius="2"` for a 4px slider track, `CornerRadius="3"` for a 6px progress bar, `CornerRadius="1.5"` for a 3px tab indicator, `CornerRadius="3"` for a 6px scrollbar thumb). `CornerRadiusFull` is strictly reserved for fixed 1:1 square elements where `Width == Height` (e.g. 16x16 notification badges, circular icon buttons). Never wrap dynamic toolbar collections (`PART_PanelMainItems`) in an outer pill container.
- **ThemeModifier Icon Buttons**: ThemeModifier hardcodes its edit (✏) and X (restore) buttons at `Width="41"` with no height, inside two fixed 41px columns (editor XAML and constants code). Each theme's base `Button` style adds a `Width == 41` trigger that renders them as a **41x41 square** with a small centred glyph and inner breathing room: `Padding="0"`, `HorizontalContentAlignment`/`VerticalContentAlignment` = `Center`, `MinWidth` 41 and `MinHeight` 41 (the square, pinned — a theme's own `MinWidth`, e.g. MUI's 64, would otherwise coerce the plugin's buttons wider), and `FontSize` 16, so the icon stays minimal and is never clipped by `ButtonPadding` (auto-width buttons keep their padding). Width must stay 41 and the glyph small — larger makes the buttons read oversized, wider makes the two overlap. `validate-extension.ps1` enforces the trigger on every theme.
- **Sidebar Icon Sizing**: In `SidebarItem` templates, never stack a fixed plate padding (e.g. `Padding="14,12"` on a 44x40 item) with `{Binding IconPadding}` (default 8 per side). The two sum past the item size, the icon Viewbox collapses to 0px and add-on sidebar icons vanish (hit Tumbleweed, NightCity). Use exactly one: either bind `IconPadding` with no extra padding, or a fixed plate padding with no `IconPadding`. Content area must be >= 16x16. After editing a sidebar, check an add-on item (not just Library/Statistics, which use the separate `SetIcon`) is visible.
- **Game Page Layout**: SteamScreenshots in left column above description; metadata on right. Game banner spacer scales proportionally with HeroArt via MathConverter (`'x * <DefaultSpacer> / <DefaultBanner>'`), keeping default title/gradient scrim positions intact while moving top elements up/down dynamically when Banner height (0 = off) is modified.
- **Icons & Brushes**: Add-on tile icons (`info/icon.png`) use default orange (`#FF7A1A`). Themes use brushes only (never `Color` keys).
- **New Theme Reference Research**: When modeling a theme after a reference without ready tokens (game, film, OS, design system), **conduct deep research before coding/scaffolding**. Gather data from screenshots/captures, reference codebases/repos, style guides, or specs: measure colors, identify typography/fallbacks, study chrome/selection styles and icons, and log all sources/rules in `RESEARCH.md` (and link from `AGENTS.md` -> `Sources`).
- **Theme Screenshots & Mockups**: All release screenshots (`screenshot-details.png` and `screenshot-settings.png` in `art/`) are generated exclusively from the HTML preview templates (`art/preview-details.html` and `art/preview-settings.html`) via `.\scripts\take-screenshots.ps1 -Extension <key>`. Never capture live Playnite desktop windows. Screenshot files always carry the `screenshot-` prefix (`screenshot-<view>.png`: `screenshot-details.png`, `screenshot-settings.png`); a bare `details.png`/`settings.png` is never a screenshot (those names belong to icon-set images such as `Images/<Set>/settings.png`). Every link to a screenshot (README, listing `Screenshots:` URLs, docs) uses the prefixed name. Previews are 1280x720 and are not scaffold output: build them per `.claude/skills/playnite-theme-dev/previews.md` after the reference research, with colors as `var(--token)` from the theme's `src/tokens.css` (injected at render time), real sizes/fonts/icons/control states, and the source's signature motifs. Fonts in previews are bundled open fonts (`scripts/fonts/`, `scripts/data/fonts.json`; Windows names such as Segoe UI map to stand-ins), so renders are identical on any machine: name only bundled fonts, no `system-ui`, and fix any `system font used` warning. After changing tokens or XAML, run `validate-extension.ps1` (lists preview colors that drifted) and re-render.
- **Trademarks & Branding** (Playnite add-on guidelines): A theme must never be branded as an official product of the owner it imitates (GitHub, Microsoft, Google, a game studio, ...). Give it its own abstract name that only echoes the source ("Fluence" for Microsoft's Fluent, "Primo" for GitHub's Primer) or a plain "<Source>-inspired" name; "The Official Microsoft Fluent Theme" is not acceptable. Never put an owner's logo or mark in a tile, icon or preview. Every theme modeled on someone else's design system, app or game says in its listing `ShortDescription`/`Description` and in `info/NOTICE-<Dir>.txt` that it is unofficial and not affiliated with, endorsed by or sponsored by the owner, and says "inspired by", never "by"/"official". Design-system names appear only as nominative references. A released add-on keeps its `Id`, key and folder when only the display name changes.
- **PRs/Releases**: One GitHub Release & one PlayniteAddonDatabase PR per add-on. Show PR copy to user before pushing. Database PR body must link screenshots (embed each `Screenshots: Image:` URL as a markdown image; if no `Screenshots:`, say so).

## Skills (`.claude/skills/`)
- `playnite-plugin-dev`: .NET plugin work, settings UI, localization, debugging.
- `playnite-theme-dev`: Theme creation, token swaps, control restyles, key vocabulary.
- `playnite-release`: Versioning, packaging, PlayniteAddonDatabase PRs.

## Context & Token Efficiency
- **Targeted file reads**: Never view entire large XAML (>200 lines) or JSON files; grep for target symbols first, then inspect only the relevant line slice (`StartLine`/`EndLine`).
- **Subagent delegation**: Delegate multi-theme surveys, wide grep searches, or background investigations to `research` subagents so intermediate tool outputs do not enter the primary conversation context.
