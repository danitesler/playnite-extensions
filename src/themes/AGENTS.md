# Themes — shared anatomy

Every theme here is **standalone** (it never reads another theme's files) but they are all built the same way: the same folder layout, the same Playnite files, the same key vocabulary, and the same page skeletons. This file describes what they share, so each theme's own `AGENTS.md` only records what is specific to its design system.

Rules that make Playnite load a theme (overlays, `DynamicResource`, brushes only, placeholders, build checks) are in **`docs/themes/reference.md`**; the step-by-step for a new theme is skill **`playnite-theme-dev`**.

Multi-theme fix (shell, game page, sidebar across all registered themes): **`docs/themes/theme-patch-workflow.md`**.

## Shell

- **Grid details width**: `Views/LibraryGridView.xaml` preserves Playnite's configured `GrdiDetailsWitdh` as the preferred width and caps `PART_ControlGameView.MaxWidth` at the templated library view's `ActualWidth`. Narrowing the window (or opening filters) must shrink the outer panel; widening it restores the configured width. Keep this separate from the responsive content inside `GridViewGameOverview.xaml`. Run `pwsh -STA -File tests/wpf/GridDetailsPanelWidthRegressionTests.ps1`.
- **Top bar order**: search, filter toggle, then sorting at the top left in every theme. `PART_PanelMainItems` is a content-sized Grid: template-based column triggers put sorting first despite Playnite's insertion order. Keep the host and button heights explicit and equal to the theme's toolbar button height, including filter/notification plates and active states. Run `pwsh -STA -File tests/wpf/TopPanelLayoutRegressionTests.ps1` after shell changes.
- **Persistent search magnifier**: keep the glyph outside `PART_SeachIcon`, which Playnite hides on focus or nonempty text. Empty/unfocused uses `TextBrushDarker`; focused or nonempty uses `GlyphBrush`. Retain `ShowImage=False` behavior for fields that explicitly disable the image, and reserve icon space while typing. Cover overrides in `Views/TopPanel.xaml` and MannCo's keyed template too. Run `pwsh -STA -File tests/wpf/SearchGlyphRegressionTests.ps1`.
- **Search clear hit area**: `PART_ClearTextIcon` keeps an explicit ContentControl template with a transparent Border around its ContentPresenter. Playnite handles MouseUp on this part; the glyph alone may reject hits or only respond on its strokes. Run `pwsh -STA -File tests/wpf/SearchClearRegressionTests.ps1`.

Each theme lays the shell out its own way; the mechanics are the same:

- **Side panel close button**: The grid view side panel's close button (`CloseGameSideBarCommand` in `Views/GridViewGameOverview.xaml`) is a 28x28 plate in the panel's top-left corner, 12px from the left and top, clear of the scroll bar. When the configured `GameBannerHeight` is below 120px, or `{Settings ShowBackgroundImageOnWindow}` is on (the game pages collapse the banner then, so the corner would sit over the icon), show it inline immediately left of the game icon instead, vertically centered with a 10px gap. Do it in the two buttons' style triggers: the inline style's `ShowBackgroundImageOnWindow` trigger sets `Visible`, the corner style's sets `Collapsed` and comes before the `Game=null` trigger. Keep the inline button fixed at that position while the content scrolls. At 120px and above keep the corner placement. Both placements share the same template and update immediately when ThemeModifier changes the setting. With no game selected (including a null DataContext), always show the corner close regardless of banner height; keep it outside selected-content visibility. It reads at rest (the theme's `ButtonBackgroundBrush` plate, a `NormalBorderBrush` rim, a 14px `TextBrush` glyph from `IconWindowClose`) and has an animated hover: a `DangerBrush` plate fades in over 0.12s and the glyph turns `DangerForegroundBrush`. Never a bare glyph on the banner art. If an `art/` generator writes the overview, change the generator too. `validate-extension.ps1` checks size, corner and hover. Bind the inline button’s render translation to the physical scroll offset and stack its header above the scrolling content. Run `pwsh -STA -File tests/wpf/SidePanelCloseButtonRegressionTests.ps1`.
- **Active-state indicators**: Never print a word for an active state (no "Filter Active" label, no `LOCFilterActiveLabel` in `TopPanel.xaml`). The top panel's filter toggle shows a small mark on the top-right corner of its icon while Playnite sets its `Tag` to True: 7-10px, in the theme's own shape from its source (dot for design systems, square for pixel and terminal games, diamond for fantasy and heraldic, slanted or chamfered plate for Persona, Overwatch, Cyberpunk and StarCraft style), filled with `{DynamicResource DataChangeNotifBrush}` (the notification accent, always a branded colour that differs from the muted icon), `IsHitTestVisible="False"`, collapsed by default. Same rule for any other "something is on" state a theme adds. `validate-extension.ps1` fails a theme that prints the label or has no mark. Use `TextFilter` to keep the Default triggers, or name the mark `Dot`.
- **Running game indicator**: the launching or running game is framed and tinted in the running colour (`RunningFrame`, `RunningWash`) with the theme's own motif on its details row, cover, list view row (`DefaultControls/ListView.xaml` overlay, row style only) and over the game page's Play / context action cell (`RunningActionIndicator` in `PlayButton.xaml`, placed by both overviews). `RunningIndicatorBrush` is a different hue from the Play button, selection and hover. The action button keeps Play's plate and fills it with that colour while launching or running; the overlay copies the plate, it does not paint a rectangle outside it. Launching is a progress sweep (a band crossing the item's own shape, a foot line filling, the theme's mark reacting as it lands; `RunningScan`, `RunningFill`) on the button, both rows and the cover. Running is a slow idle pulse (frame 0.7 to 1, the mark idling, 2.4-4s) on those same surfaces; the RUNNING button shows Cancel only while the button itself is hovered (`RelativeSource Self`, never `TemplatedParent`) and keeps its label at 4.5:1 or better. Recipe, kit and levers: `docs/themes/running-motion.md`; look at it with `tests/wpf/RunningMotionFrames.ps1`. Named storyboards are removed on exit. Recipe: `docs/themes/reference.md` -> Running game indicator. `validate-extension.ps1` enforces it; run `pwsh -STA -File tests/wpf/RunningIndicatorRegressionTests.ps1 -Keys <key>` on a build drop.
- **Window buttons** are drawn by `MainWindowStyle.xaml` (`MainWindowButton`). The top bar keeps their width clear on its right (plus a gap), and a sidebar docked at the top or bottom does the same. Change one, change the other.
- **Main menu**: `PART_ElemMainMenu` uses `MainMenuButton`, in the sidebar; the top bar shows it only when the sidebar is hidden.
- **Sidebar** is designed for the **left** (Playnite's default): a compact vertical rail at the window's left edge with the main menu button at its top — 44px wide, items 44x40 with 16px glyphs (32px plates where the design uses plates), main menu button 44 wide. Right mirrors it; top and bottom are fallbacks drawn as a strip. No theme asks users to move the sidebar.
- **Library background art** (`Views/Library.xaml`): where a theme feathers it, the `OpacityMask` sits inside a `BitmapCache` wrapper (as for every masked image).
- **View switches are icons only** (`Views/TopPanel.xaml`): `TopPanelSwitchDetailsViewTemplate`, `TopPanelSwitchGridViewTemplate` and `TopPanelSwitchListViewTemplate` draw `IconDetailsView` / `IconGridView` / `IconListView` through `IconTemplate` at `IconSize`. No text word labels. `TopPanelItem` already exposes the item's `Title` as its tooltip.
- **Layers**: at most three surfaces, named by shared keys: `ShellBackgroundBrush` (frame, rail), `TopPanelBackgroundBrush` (top bar), `ContentBackgroundBrush` (the library layer), on `WindowBackgourndBrush`.

- **Sidebar Icon Sizing**: In `SidebarItem` templates, never stack a fixed plate padding (e.g. `Padding="14,12"` on a 44x40 item) with `{Binding IconPadding}` (default 8 per side). The two sum past the item size, the icon Viewbox collapses to 0px and add-on sidebar icons vanish (hit Tumbleweed, NightCity). Use exactly one: either bind `IconPadding` with no extra padding, or a fixed plate padding with no `IconPadding`. Content area must be >= 16x16. After editing a sidebar, check an add-on item (not just Library/Statistics, which use the separate `SetIcon`) is visible.
- **Whole-button hit area**: Every custom `Button` template (cover hover `GridTileButton`, More, Edit, caption and toolbar buttons) has a root with `Background="Transparent"` (or a brush), so the whole plate hovers, presses and clicks, not only the glyph or text inside it. Decorative layers inside use `IsHitTestVisible="False"`. `validate-extension.ps1` checks `GridTileButton`.

## Game page

`DetailsViewGameOverview.xaml` (details view, right pane) and `GridViewGameOverview.xaml` (grid side panel) share one skeleton, top to bottom:

1. **Banner** (`HeroArt`): `PART_ImageBackground` as a band of height `GameBannerHeight` (shared key in `Common.xaml`, default 320; ThemeModifier edits it, 0 to 600). Masked to fade out downward, a page-colored scrim darkens it toward the title, all in a `BitmapCache` wrapper. It collapses when the game has no background art or Playnite hides the image; 0 turns it off.
2. **Room above the title**: a spacer whose height scales proportionally with `HeroArt` via Playnite's global `{StaticResource MathConverter}` (`HexInnovation.MathConverter`):
   ```xaml
   <Setter Property="Height" Value="{Binding ActualHeight, ElementName=HeroArt, Converter={StaticResource MathConverter}, ConverterParameter='x * <DefaultSpacer> / <DefaultBanner>'}" />
   ```
   In both details and grid views, floor the spacer so the visible header retains the content’s side gutter at low or zero banner heights; account for the header’s own top margin. The zero-height and collapsed-art triggers use the same floor (collapsed art retains its prior ActualHeight). Materia’s in-flow media uses a separate gutter spacer. Each view uses its own side inset and existing header margin to determine the minimum, while keeping its proportional expression unchanged.
   This ensures:
   - **Exact default alignment**: At default `GameBannerHeight`, the ratio `x * <DefaultSpacer> / <DefaultBanner>` produces exactly `<DefaultSpacer>`. The title and header sit in their designed position over the darkened gradient scrim of the banner rather than being pushed down into empty solid background.
   - **Dynamic scaling with ThemeModifier**: When the user adjusts "Banner height (0 = off)" in ThemeModifier, decreasing the value shifts top elements closer to the top (down to the minimum gutter in each view), and increasing it shifts them further down proportionally. Never bind spacer height directly to `{DynamicResource GameBannerHeight}`.
3. **Header**: `PART_ImageIcon` and `PART_TextDisplayName`, then the actions (`PART_ButtonPlayAction` and `PART_ButtonContextAction` stacked in one cell, `PART_ButtonMoreActions`, `PART_ButtonEditGame`). Details view: actions beside the title. Grid panel: actions under it, and a close button (`CloseGameSideBarCommand`) over the top-left corner, or inline left of the icon when configured banner height is below 120px.
4. **Responsive content**: Steam screenshots, description (`PART_HtmlDescription`) and notes form the main column. In both views metadata sits beside it at the preferred width when the body fits that width, the theme gap and 400px for content. Below that, metadata fills the space underneath, with two columns at 560px of usable inner width and one column below 560px. See `docs/themes/reference.md` -> Responsive game pages. The entire section is enclosed in an independent `SteamScreenshotsGameScope` parent that defaults to Collapsed and allows only the current `Game.PluginId` = `cb91dfc9-b977-43bf-8e70-55f46e410fab` OR `Game.Source.Name` = `Steam`. This parent stays outside loading animations: the plugin flag can complete late for a previously selected Steam game, and animation clocks outrank setters. Host is `SteamScreenshots_SteamScreenshotsViewControl`, shown inside that gate while `{PluginSettings Plugin=SteamScreenshots, Path=IsControlVisible}` is true, plus a 12 s skeleton for Steam games (the plugin hides its control on every game change and needs about a second). The bindings use `FallbackValue=PluginUnavailable` (not `False`), so with the plugin missing or disabled neither the section nor the skeleton shows. Name trigger timers and remove them on exit, or reset per-game timers from `Game.Id` target updates (ColdSeat). Preserve the gate in art generators. Run `pwsh -STA -File tests/wpf/SteamScreenshotsRegressionTests.ps1` and verify Steam loading -> non-Steam -> late completion, initial non-Steam, cleared selection and details/grid switching.

5. **Empty state in both views**: `GridViewGameOverview.xaml` and `DetailsViewGameOverview.xaml` must hide game content and show a designed `LOCErrorNoGameSelected` empty state, centred in the viewport, when `{Binding Game, FallbackValue={x:Null}}` is null. On the details `PART_ScrollViewHost`, set `Visibility="Visible"` explicitly so the inherited `DetailsScrollViewer` style cannot collapse the empty state on a null DataContext. Check both an initially empty selection and selected game -> grid -> details with selection cleared, then select a game again. Grid empty states always retain the top-left CloseGameSideBarCommand button, outside the selected-content gate and independent of the banner setting. Preserve this behavior in overview generators. Required for new themes; recipe in `docs/themes/reference.md` -> Interactive layer.

Run `pwsh -STA -File tests/wpf/GamePageBreakpointsRegressionTests.ps1` for responsive layouts, and `pwsh -STA -File tests/wpf/DetailsViewLayoutRegressionTests.ps1` plus `pwsh -STA -File tests/wpf/GridOverviewLayoutRegressionTests.ps1` for banner and gutter sizing. Check heights 0, 5, 10 and 20px.

### Metadata pane

Every field of Playnite's "Game fields to be displayed on details panel" list lives in **one** pane, never split between a header, stat cards or chips elsewhere. Six groups, in this order, each field a container `x:Name="PART_Elem<Field>"` (Playnite toggles its `Visibility`) holding a label (a Playnite `LOC` key) and the value part:

| Group (`x:Name`) | Fields |
|------------------|--------|
| `MetaProgress` | CompletionStatus, PlayTime, LastPlayed, RecentActivity, Added |
| `MetaScores` | CommunityScore, CriticScore, UserScore (`TextBlockGameScore`) |
| `MetaAbout` | Developers, Publishers, ReleaseDate, Series, AgeRating, Region |
| `MetaTags` | Platform, Genres, Categories, Features, Tags (`Tag="Chip"` `WrapPanel`) |
| `MetaLibrary` | Library, Source, Version, InstallSize, InstallDirectory |
| `MetaLinks` | Links |

- A group is a `Border` that collapses through a `MultiDataTrigger` on `{Binding Visibility, ElementName=PART_Elem<Field>}` = `Collapsed` (a `DataTrigger` for one field), so a game with few fields shows few groups and no stray separator.
- Separator between groups: a 1px top border on each group inside a `ClipToBounds` wrapper whose inner panel has negative top and bottom margins, so the first group draws no rule; or plain space where the design system has no rules.
- Rhythm: 12px above and below each group rule (Primo 16), 8px above and below each field (Materia details 6, Questlog 6), 4px between a caption and its value in the grid panel. The wrapper's negative margins are `-(2 x group + 1 + field)` on top and `-field` at the bottom; change them together with the spacing. The grid panel keeps 20-24px side padding and a 24px gap between its two columns.
- No group captions: a theme cannot ship a `Localization` folder, so labels are existing Playnite keys (`LOCTimePlayed`, `LOCDevelopersLabel`, `LOCGenresLabel`, ...).
- Both views place captions beside values. Grid-pane rows use proportional caption/value columns (2*:3*) with a 12px gap and wrapping text. Preserve each named field and its visibility handler. Not `GridEx`: `AutoLayoutColumns` would put hidden rows back in the flow.
- `GameDetailsPaneWidth` and `GridDetailsPaneWidth` both default to **300px of usable metadata content**. Bind the width inside horizontal padding and borders so a decorated pane has the same room for labels and properties as Attache's bare pane. Let the surrounding frame size to its content, preserve its exterior gap, and keep both resources dynamic for ThemeModifier.
- Values in lists (`PART_Items*`) are Buttons Playnite styles with `{StaticResource PropertyItemButton}` from code. `PropertyItemButton.xaml` is the only hook: a text link by default, a chip when the owning list has `Tag="Chip"` (a `RelativeSource AncestorType=ItemsControl` DataTrigger).
- `HtmlTextView` takes `Color`s: set `TextElement.Foreground` and `Tag` to brushes and bind `HtmlForeground` / `LinkForeground` to `(TextElement.Foreground).Color` / `Tag.Color`.

## Icons

Add-on tile icons (`info/icon.png`) use default orange (`#FF7A1A`). Themes use brushes only (never `Color` keys).

- **UI icons**: `Icon<Role>` geometries in `Media.xaml`, drawn by `IconTemplate` (stroked sets use a `DrawingImage`). Generated with `scripts/render-icons.ps1 -Format Geometry|DrawingImage`, or hand-drawn (Codex `icons/`, Questlog `art/glyphs.py`, Uplink `art/icons.py`, Ancient `Media.xaml`, Biome/Overworld `art/icons.py` Pixelarticons).
- **Menu icons Playnite copies** (`AddGameIcon`, `PlayIcon`, ...): Playnite rebuilds them from a `TextBlock`'s glyph and font, so a vector is lost. Either keep Playnite's icofont glyphs and only recolor them (Shade, Chakram, Materia, Fluence), or map each key to a theme-relative PNG path as `sys:String`, rendered by `render-icons.ps1 -Extension <key>` from `icons.json` (Primo, Battle.net, Assassin's Creed) or by the theme's own art script (Biome, Overworld, WoW Vanilla).

## Previews and screenshots

All release screenshots (`screenshot-details.png` and `screenshot-settings.png` in `art/`) are generated exclusively from the HTML preview templates (`art/preview-details.html` and `art/preview-settings.html`) via `.\scripts\take-screenshots.ps1 -Extension <key>`. Never capture live Playnite desktop windows. Screenshot files always carry the `screenshot-` prefix (`screenshot-<view>.png`: `screenshot-details.png`, `screenshot-settings.png`); a bare `details.png`/`settings.png` is never a screenshot (those names belong to icon-set images such as `Images/<Set>/settings.png`). Every link to a screenshot (README, listing `Screenshots:` URLs, docs) uses the prefixed name. Previews are 1280x720 and are not scaffold output: build them per `docs/themes/previews.md` after the reference research, with colors as `var(--token)` from the theme's `src/tokens.css` (injected at render time), real sizes/fonts/icons/control states, and the source's signature motifs. Fonts in previews are bundled open fonts (`scripts/fonts/`, `scripts/data/fonts.json`; Windows names such as Segoe UI map to stand-ins), so renders are identical on any machine: name only bundled fonts, no `system-ui`, and fix any `system font used` warning. After changing tokens or XAML, run `validate-extension.ps1` (lists preview colors that drifted) and re-render.

How to build them (tokens as `var(--token)`, real sizes and states, signature motifs, 1280x720, checklist): `docs/themes/previews.md`. The renderer injects `src/tokens.css`; `validate-extension.ps1` lists preview colors that drifted from it; `node scripts/preview-tokens.mjs link src/themes/<Name>` converts matching hex to `var(--token)`.

Fonts: previews render with bundled open fonts (`scripts/fonts/`, registry `scripts/data/fonts.json`), the same on any machine. A Windows or commercial font a theme asks for (Segoe UI, Consolas, Bahnschrift, Georgia, Impact, ...) is drawn with its open stand-in; see previews.md -> Fonts.

Not a full-screen page and not a tab strip. Layout rules and `data-part` tags: `docs/themes/previews.md` -> Layout.

## Statistics page

Playnite's Statistics view lays its sections (Overview, Completion Status, Top play time, Library, ...) out as `GroupBox`es in a wrapping panel, so every section is a compact card sized by its content, several per row. Never restyle that view, and never give a `GroupBox` template a child that reports a large desired width: a `Path` or `Line` with `Stretch="None"`/`Fill` wider than ~200px (hazard stripes, rules, ornaments), a fixed `Width`/`MinWidth` >= 200, `HorizontalAlignment="Stretch"` plus a fixed-size art, or a `Control` whose template does any of these (`Template="{DynamicResource ...}"`). One such child makes every section ask for the whole page, so the cards stack full width with large empty areas (hit Blacklist's 2600px hazard Path, Cordon's `Line`). Follow Ayywi's `DefaultControls/GroupBox.xaml`: a content-sized `Border` with a header and a body, no fixed widths. Decoration that must span the card goes inside a `Canvas` (no desired size) in a `Grid` with `ClipToBounds="True"`; use `Rectangle`/`Border` for rules. Any shared template used in a GroupBox (dividers, stripes, chamfers) follows the same rule. After touching `GroupBox.xaml`, a template it uses, or `HazardStripesTemplate`-style art, open Statistics in Playnite and check the sections wrap as cards. `validate-extension.ps1` flags wide Paths, `Line Stretch=Fill` and fixed widths >= 200 in the GroupBox template and the templates it references.

## ComboBox chevron room

In a `ComboBox` template the selected value (`ContentSite`) and the dropdown chevron share one cell, and the box is only as wide as its value, so a value with no space reserved on its right runs under the arrow and the chevron looks hidden (Blacklist's "English", "Minimize"). Always reserve the chevron: wrap `ContentSite` in a `Border` with `Margin="0,0,R,0"` where R = chevron width + its right margin + 8px (or put the value and the chevron in separate grid columns, as Ayywi does), and keep `PART_EditableTextBox`'s right margin equal to R. `validate-extension.ps1` fails a `ComboBox.xaml` whose `ContentSite` reserves less than 12px on its right. Check a short value ("Minimize") and a long one in Settings after touching the template.

## Form field height

Form fields and buttons use **32px** in every theme (`ControlHeight` in `Common.xaml`, never another value), except filter sidebar fields and preset controls, which are **28px**; their full rules are in `docs/themes/reference.md` under Hard rules. That covers `TextBox`, `PasswordBox`, `ComboBox`, Playnite's `ComboBoxList` / `DdItemListSelectionBox` / `Filter*SelectionBox`, `DatePicker`, number and path boxes, and `Button`, so fields on one row of a settings or edit form line up. Base styles take `MinHeight` = `ControlHeight` (on `Button` through a `Height = NaN` trigger, so explicit sizes survive; multi-line text boxes still grow). `InputPadding` and `ButtonPadding` vertical padding is 5 (4 with thick borders), small enough that `ControlHeight` decides the height whatever the font. Never apply `Padding` twice on a text box: WPF already passes it to `PART_ContentHost`, so no `Margin="{TemplateBinding Padding}"` on the host and no `Padding` on the `Border` around it. Inner boxes (`PART_EditableTextBox`, `PART_TextInpuText`, `BareTextBox`) reset `MinHeight` to 0. Playnite hard-codes 24px on its list dropdowns and no theme template reaches them, so `CustomControls/ComboBoxList.xaml`, `FilterSelectionBox.xaml`, `NumericBoxes.xaml`, `PathSelectionBox.xaml` and `DefaultControls/DatePicker.xaml` are required overlays (`new-theme.ps1` writes them). `SearchBox` keeps its own shell height. `validate-extension.ps1` enforces all of this (`FormControlHeight`). Check the sidebar and a game edit dialog.

## Game page action buttons

Next to Play on the game page (details view and grid side panel), the secondary buttons (`PART_ButtonMoreActions`, `PART_ButtonEditGame`, and any other secondary action) are **icon-only**: a glyph from `Media.xaml` (`IconOptions`, `IconEdit`) in a fixed-width square button (`Padding="0"`), no text label; the label goes in `ToolTip` (`LOCMoreAction`, `LOCEditGame`). Play (and the context action) keep their text. More and Edit are the **same fixed square** (`Width == Height`, identical on both, e.g. 40x40) and both carry a `ToolTip` (More / Edit) so hovering names them. The Edit button is **always visible**: never hide it (`Visibility="Hidden"`/`Collapsed`) or reveal it on hover (a `DataTrigger` on `IsMouseOver` of an ancestor), so ThemeModifier-style discoverability and touch work. `validate-extension.ps1` fails a labeled More button, a hover-only Edit button, unequal More/Edit sizes and a missing ToolTip. Use the theme’s 16–20px glyphs through `IconTemplate`.

## Control corner radii and shapes

- **Why `CornerRadiusFull` distorts in WPF**: Unlike CSS (which scales corner radii uniformly), WPF's `Border` clamps horizontal and vertical radii independently: `radiusX = min(radiusX, width/2)` and `radiusY = min(radiusY, height/2)`. When a single huge radius (e.g. 9999 or 10000) is set on an element where `width != height`, WPF draws an ellipse/oval across the entire element rather than flat edges with circular caps.
- **Base control styles must use `ControlCornerRadius`**: Generic `<Style TargetType="{x:Type Button}">`, `<RepeatButton>`, `<ToggleButton>`, `<SearchBox>`, `<TabControl>`, and menu items MUST use `{DynamicResource ControlCornerRadius}` (or theme-appropriate small radius, e.g. 4-12px), NEVER `CornerRadiusFull` (pill/stadium 9999+). In WPF, plugins (e.g. SteamScreenshots carousel navigation `<` and `>`, numeric spin buttons) and unconstrained dialogs inherit base styles; large radii on non-standard aspect ratios distort them into vertical ellipses/ovals.
- **Action buttons (`PlayButton`) must use `ControlCornerRadius`**: The primary CTA on the game page must use `{DynamicResource ControlCornerRadius}` so its corner curvature matches adjacent secondary action buttons (e.g. `... More`, `Edit`).
- **Metadata tag chips (`PropertyItemButton`) must use `ControlCornerRadius`**: Genre, feature, category, tag, and platform chips have variable text length. Setting `CornerRadiusFull` causes wide tags (e.g. "Turn-based strategy (TBS)") to become extreme horizontal ovals. Always use `{DynamicResource ControlCornerRadius}` (or `CornerRadiusSmall`).
- **`CornerRadiusFull` is strictly for fixed 1:1 square elements**: Reserve pill/full radius ONLY for elements where `Width == Height` (e.g. 16x16 notification count badges, circular icon buttons).
- **Thin tracks and progress fills must use half-thickness radii**: `Slider` tracks, `ProgressBar` bars, active tab indicator lines, and scrollbar thumbs (`ScrollBarThumb`) must NEVER use `CornerRadiusFull` (which clamps horizontal radius to `width/2`, turning a 4px or 6px line into an elongated needle/spindle). Always specify an explicit numeric radius equal to half the track thickness (e.g. `CornerRadius="2"` for a 4px slider track, `CornerRadius="3"` for a 6px progress bar or thumb, `CornerRadius="1.5"` for a 3px line).
- **Scrollbar thumbs (`ScrollBarThumb`)**: Use half track width (e.g. `CornerRadius="3"` for a 6px thumb) or `CornerRadiusSmall`, never `CornerRadiusFull`. Large numbers scale disproportionately across axes in WPF's Border geometry and distort when rotated horizontally.
- **No pill wrappers on dynamic toolbars**: Never wrap dynamic collections like `PART_PanelMainItems` in an outer pill container.
- **Fixed-width buttons (ThemeModifier icon buttons)**: ThemeModifier hardcodes its edit pencil and restore X at `Width="41"` in fixed 41px columns. Keep the base `Button` style's `Width == 41` detection trigger; local plugin widths cannot be overridden by a style setter. Pin `Height`, `MinWidth`, `MinHeight`, `MaxWidth` and `MaxHeight` to 41 internally, set `Padding="0"`, both content alignments to `Center`, and `FontSize` to 16. Apply a uniform `LayoutTransform` with `ScaleTransform ScaleX="0.7804878048780488" ScaleY="0.7804878048780488"` (32/41): the button occupies **32x32px** in layout and its glyph, border and decoration shrink proportionally, including explicitly sized child glyphs. Do not use `RenderTransform`, which leaves the old layout size. Auto-width buttons keep their normal padding. `validate-extension.ps1` enforces the square and scale on every theme.

## Tab colours

Tab pages inherit the selected `TabItem`'s `Foreground`: the game edit dialog's field labels are `TextBlock`s with no colour of their own. So the `TabItem` keeps `TextBrush`, and every header colour (idle, hover, selected) goes on the `TextBlock` around the header with `TargetName`. Never leave a `Foreground` setter on the tab itself: dark text for a bright selected plate made Backbeat's labels unreadable. That `TextBlock` around `ContentPresenter ContentSource="Header"` is required too: the dialog's headers bind `Foreground` to an ancestor `TextBlock`, and without one they render black. `validate-extension.ps1` enforces both (`TabItemColors`).

## Settings screen

Every theme restyles Playnite's Settings window (and every dialog) with its own chrome, drawn from its source: `DefaultControls/TreeView.xaml` (section list rows are full-width plates 28-32px tall in the normal body font (no heading face or caps) with separate hover, selected and keyboard-focus states; the selected row changes two or more named parts and uses the source's own selection motif; `WindowSettings`/`WindowExtensions` width DataTriggers 240-280 that also set `VerticalScrollBarVisibility=Visible` so opening a node never makes a scroll bar appear and reflow the window) and `DerivedStyles/StandardWindowStyle.xaml` + `WindowBarButton.xaml` (36-48px title band, `CaptionHeight` equal to the content offset, one signature graphic in XAML vectors filled with theme brushes, `PART_*` names kept). Never leave Playnite's text-link list and flat title bar. Rules, motif table and pitfalls: `docs/themes/settings-screens.md`. `validate-extension.ps1` fails a theme without both files and prints `settings chrome:` advisories for sizes.

## Window background

Game art behind the library comes only from Playnite's "Use game background image as window background" (Settings, Appearance, General); themes add no ThemeModifier option for it. `Library.xaml` shows `PART_ImageBackground` at full strength (no theme scrim, tint, mask, opacity or blur: Playnite's darken and blur settings are the treatment), top-aligned in a grid sized to the art with a gradient that fades its bottom edge into the color behind it (`WindowArtSwatch`), so the art never ends in a hard line. The art, its fade and any decor sit in one layer (a `Grid` before `TopPanel`, `Grid.RowSpan="2"`, its Background the fade color while the setting is on) that spans the top bar and reaches under the icon rail by the rail's thickness (Margin `-44,0,0,0`, mirrored, or `-56` at the top or bottom, by `{Settings SidebarPosition}`), so the art is one picture across the window; Shade keeps its rail outside the card and does not reach under it. While `{Settings ShowBackgroundImageOnWindow}` is True the top bar, the rail (`Sidebar.xaml`: its solid fill, plus any decor that depends on it, such as Medallion's brush edge or Fluence's rounded layer corner), filter and explorer panels, game pages and Expander headers (every theme ships `DefaultControls/Expander.xaml` with the trigger) turn transparent, scroll bar track fills drop to 0.4 opacity, and `HeroArt` collapses, so `GameBannerHeight` has no effect; the theme's `Slider` style disables ThemeModifier's banner height and banner darkening sliders then (each row label's `Tag` is the key). With the setting off, `GameBannerDarken` (ThemeModifier slider 0-1, default 0, in `Common.xaml`) sets the opacity of a `Rectangle` filled with `GameBannerTintBrush` right after the banner's `PART_ImageBackground`, under the theme's own fade; a second 50% layer in the same brush (`Tag` = the value, collapsed at 0) makes any value above 0 start at 50%, so the result is 50% + 50% x the slider. `GameBannerTintBrush` (Constants, editable in ThemeModifier) is a dark color from the theme itself, never plain black unless the theme is black: its `ArtTintBrush` when it has one (Tumbleweed red, Hearthside wood), otherwise its darkest branded surface (Ace olive `NormalBrush`, Dropzone navy). Overview generators carry the same triggers. Details: `docs/themes/reference.md` -> Window background. `validate-extension.ps1` enforces it (`Test-WindowBackground`).

## Bundled fonts

Previews and Playnite draw the same faces. A font stack starts with a font every Windows has or with a face bundled in the theme's `src/Typography/` (`./Typography/#Family`, never `Fonts/`, which packing skips), never with a font users lack: the preview would show its stand-in and Playnite a fallback (Relay's Orbitron title showed as Bahnschrift). Bundle open fonts only (OFL, from `scripts/fonts/`, with `OFL.txt`), as static TTFs (WPF ignores variable axes), and only the weights and styles the theme sets for that key, trimmed to Latin and Cyrillic (`scripts/subset-theme-fonts.py`) unless the license reserves the font's name. Name the font in `info/NOTICE-<Dir>.txt`. `validate-extension.ps1` fails a mismatch, a missing or unreferenced face and a missing license (`scripts/theme-fonts.mjs`). Details: `docs/themes/reference.md` -> Bundled fonts.

## Per-theme notes

A theme's `AGENTS.md` keeps only what is its own, in this order:

1. **What this is**: design system, version, dark variant; the unofficial / no-owner-assets statement for every theme modeled on someone else's design system, app or game ([Trademarks & Branding](#trademarks--branding): given its own abstract name or a plain "<Source>-inspired" name, never an official-sounding one; ships `info/NOTICE-<Dir>.txt`).
2. **Sources**: reference notes in `RESEARCH.md` (token package, component specs, icon set, captures, each with version and license); `AGENTS.md` links to it.
3. **Tokens**: which token plays each key (Playnite palette first, then shared keys), plus radii and fonts.
4. **Component spacing**: the `Common.xaml` values and the spec each comes from.
5. **Shell**: the layout, per shell file.
6. **Game page**: only how it differs from the skeleton above (columns, widths, header).
7. **Components**: Playnite file → design-system component.
8. **Deviations**: where WPF or Playnite cannot follow the spec.
9. **Not verified yet**: theme-specific checks beyond the list below.
